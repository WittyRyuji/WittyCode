## 结论

上轮四个优先项都有依据，但有两处需要收窄表述：

1. **不是每条摘要路径都会先裁剪工具结果。** 当前 API 模型走文本摘要；套餐模型在原始前缀放得下时直接发送原文，只有放不下时才退到有裁剪的文本路径。
2. **页面不是每次重发整份历史。** 已有回合版本缓存，未变化的旧回合不会重发；问题是一个字的变化仍重发整个当前回合，包括已经完成的工具结果。

独立审查新增或深入复现了下面 **七类可行动问题**。最先应修的是终止事件、目标完成判定和执行前存档失败，不能仅靠减少上下文或增加自动轮次提高任务成功率。以下问题均仍未修复；其中多项是原有设计问题，并非都由上一批提交引入。

## 二、独立审查发现

### N1 · P1：收到响应终止事件之后，仍可能被当作传输中断而续接

**位置**：`desktop/core/chatgpt/responses.py:294-304`，`desktop/core/harness/loop.py:405-424,508-519`。

`read_events` 收到 `response.completed` / `response.incomplete` 后只设置 `finished`，仍继续读到 HTTP EOF；`AgentLoop._read` 也没有在已收到 `Finished` 后终止消费。若尾部连接迟迟不关闭或随即断开，已完成的响应仍进入 `failed` 分支，新续接逻辑再发恢复请求。

**实际复现**：本机 HTTP 服务正常发送全部文字／工具项及 `response.completed`，再保持连接。把读期限按比例缩短到 0.25 秒，只缩短时间，不换实现：

- 完整文字回答本应结束，却发了第二次恢复请求，两次 usage 都记账。
- 完整 `create_file` 调用及完成事件已收到，工具却没有执行；历史给它补成“用户中断，结果未知”，随后发恢复请求并最终把回合记为 done。用户没有按停止。

**影响**：额外 token／等待，完整待执行操作被误丢弃；在某些代理或网关的收尾行为下任务可能无故改道。真实远端服务的出现频率未验证。

**建议与验收**：以协议的权威终止事件为准，及时关闭底层流；区分终止前和终止后的连接问题。补“完成后保持连接／连接重置”的文字、工具和取消测试。Chat 的 `[DONE]`、Anthropic 的 `message_stop` 已有主动退出，不能用它们替代 Responses 路径的测试。

### N2 · P1：`/goal` 把 UI 的“回合结束”当作“模型正常完成”

**位置**：`desktop/core/chatgpt/controller.py:672-683`，`desktop/core/app_core.py:1893-1914`。

控制器将正常完成、输出截断、内容过滤和步数耗尽都映射为页面上的 `TurnStatus.DONE`，虽然原生存档分别保存 `done`、`incomplete`、`limit`。目标推进只看页面状态及最后文字，不检查原生终止原因，也不要求标记是工具执行后的最终回答。上轮修复了 Stop Hook 否决，但没有覆盖这些结束类型。

**实际复现**（真实 AppCore／控制器／假 HTTP）：

- `content_filter`、`max_output_tokens` 的未完成回答中有 `GOAL: DONE`，目标检查点被清除。
- 步数设为 1，助手先说 `GOAL: DONE` 再调用读取不存在文件的工具；工具报错、存档状态为 `limit`，目标仍被清除，模型甚至没有读到该工具的结果。
- 内容过滤后的文字没有完成标记时，目标层自动启动第二轮。因此“循环不会对内容过滤做传输续接”不等于整个 `/goal` 不会自动续跑。

**建议与验收**：保留可供 AppCore 判断的结构化结束原因和“最后回答是否在最后一组工具结果之后”。明确哪些原因允许目标继续，过滤／不确定结果应暂停；只有合格终态才接受完成标记。不要靠更严厉的提示词代替状态判定。

### N3 · P1：执行前检查点写失败，副作用仍被放行

**位置**：`desktop/core/chatgpt/controller.py:1093-1106,1259-1264`。

`_Watch.call_running` 在可能写入的工具前调用 `_save_pending`，但 `_save_now` 吞掉 `OSError`，不把失败传回执行入口，也不给用户显示保存失败。所谓“先落盘再执行”只有顺序，没有成功条件。

**实际复现**：把会话保存注入为 `OSError(ENOSPC)`，使用真的 `create_file` 在隔离项目写文件。两次保存尝试失败；文件仍写入 PASS；存档不存在；回合最终为 done，页面没有保存失败通知。

**影响**：会话磁盘满、权限或临时 I/O 故障时，外部操作可能已完成，但崩溃恢复没有该调用的任何检查点；后续无法可靠判断是否应该重做。

**建议与验收**：写操作前的检查点应有可观察的成功／失败结果，失败时阻止本次副作用并明确告知。普通 UI 延迟保存可以另设策略，但不能用同一个吞错函数作为执行安全门。测试 ENOSPC、权限错误、临时写失败及恢复后继续。

### N4 · P1：长工具结果在压缩前就从原生存档丢失

**位置**：`desktop/core/harness/loop.py:541-553`，`desktop/core/chatgpt/controller.py:1271-1287,1306-1309`。

`call_done` 先给当前页面完整结果，随后循环把裁剪后的文本既作为模型上下文，也写进 `SavedSession.items`；`saved.tools` 只保存状态和 diff，没有原始输出。模型预算视图与持久日志并未完全分离。

**实际复现**：注册一个只返回中性测试文字的工具，通过真实控制器及本机假模型完成一次调用。原文 **140,026 字符**，现场 transcript 保留全部；原生存档只剩 **60,036 字符**，中间验收标记消失。整个过程没有发生压缩。关闭、重新打开原生会话后，工具结果也是 60,036 字符，标记仍不存在。

**范围**：这里确认的是原生 Harness 存档与重放，不声称任何独立页面缓存都绝不可能保留副本。Shell 还会在自己的输出捕获层更早裁剪。因此仅修 `compact.render` 无法补回已经丢掉的原文。

**建议与验收**：完整结果写有界、可管理的独立附件／产物存储；上下文只带摘要、不可变引用和连续读取范围。读取引用仍执行权限与保护目录边界，不能让模型任意读整个应用存档。测试执行、重启、压缩、取消和产物保留策略。

### N5 · P2：自动摘要失败后，可用“只有用户要求”的替身覆盖执行状态

**位置**：`desktop/core/harness/compact.py:408-415,615-630`，`desktop/core/chatgpt/controller.py:1005-1023`。

自动压缩遇到摘要异常会退到 `digest`，只保留裁剪后的用户请求；已执行的工具、结果、验收证据和文件路径并不在里面。只要估算更小且放得下，控制器就接受这个替身并继续执行。它会显示退化提示，但不会暂停等待用户决定。

**实际复现**：一段包含文件创建记录及验收标记的历史在自动压缩路径遇到注入的流错误；返回 `mechanical=True`、`fits=True`，新视图约 164 个估算 token，创建路径和验收证据全不见。对照的手动压缩 `fallback=False` 会抛出错误，不接受该替身。

**判断**：这是已有的“宁愿遗忘也继续”的设计取舍，不是不可见的异常。对有副作用的长任务，它会破坏恢复依据，不能把“请求终于放得下”当作任务成功。

**建议与验收**：自动压缩失败时暂停，或保留可核对的结构化执行清单和原文引用后再继续；不能只带回用户原话就假设状态足够。需要跨压缩的任务回放，而不是仅检查压缩比。

### N6 · P2：新会话的首轮目标尚未形成真正的检查点

**位置**：`desktop/core/app_core.py:1867-1884`，`desktop/core/chatgpt/controller.py:623-625,1087-1102`。

`session.goal` 调用 `send_prompt` 后立即保存目标，但真正的 `SavedTurn` 要等异步 `_run_turn` 才创建。保存函数发现尚无 turns 就返回；创建 turn 时又没有立即调度保存。第一轮长时间思考、尚无完整输出时，目标只在内存中。

**实际复现**：新会话设置目标，本机服务只发开始事件然后等待；超过 2 秒保存周期后，内存已有目标和 running turn，但 `SessionStore.load` 仍找不到档案。

**影响与边界**：正常停止／关闭通常最终会保存；本问题是首次响应等待期间突然崩溃时，无法依赖 `/goal resume` 恢复。不是说所有已保存目标都不能恢复。

**建议与验收**：在首次模型请求前建立包含用户输入、目标和 running turn 的成功持久检查点；对新会话、恢复旧目标及等待首次输出期间的崩溃分别测试。

### N7 · P2：摘要分块的固定下限可能大于模型窗口

**位置**：`desktop/core/harness/compact.py:404-405,428-439,604-614`。

`chunk_budget` 的下限固定为 12,000，且文本摘要构造后没有检查整条请求的窗口预算，也没从分块预算扣除摘要指令、上一份摘要和协议开销。小窗口模型反而会收到更大的摘要请求。

**实际复现**：窗口配置为 4,096 和 8,192，普通文本分块路径分别发出约 **12,291 token（项目自身估算器）**的首个摘要请求；对应请求预算为 3,892 和 7,783。按同一预算拒绝超限的假服务触发机械摘要退化，而不是更小的分块。

**边界**：这是客户端预算逻辑的确定性越界；token 数是本地估算，不是提供方 tokenizer，真实服务返回 400 未验证。不是建议把所有分块机械调小。

**建议与验收**：对实际模型窗口计算可用预算，扣除固定指令、上一份摘要和输出预留；每块发送前校验完整请求。覆盖 4K／8K／常用大窗口，以及上一份摘要增长的多块情况。

## 三、建议实施顺序

1. **先保正确性**：N1 的协议终止、N2 的目标结束类型、N3 的执行前保存失败；同时修 N6 的首次目标检查点。
2. **再保上下文证据**：N4 的原始输出及受控读取，N5 的摘要失败策略，N7 的摘要预算；与上轮“裁剪丢证据”合并设计，避免只换一种截断。
3. **补完整观测**：主调用、摘要、标题、记忆分别记账，保留来源／模型和取消边界，重启不重复计入。
4. **按实测做性能改造**：把已验证的同步保存／编码和变化回合全量推送分开优化。不要把执行安全门改成无人等待的后台写入。
5. **建立固定任务回放集**：评价完成任务的总 token／耗时／成功率，包含网络收尾故障、摘要失败、上下文跨压缩及持久化错误。真实模型对照仍需另给调用上限，不能拿本轮离线探针代替。
