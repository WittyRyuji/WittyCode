## 条目

- 每个 Session 一个 droid.exe（约 300 MB）；一个会话同时只能跑一轮；SDK 只支持 asyncio（用 qasync 接 Qt）。
- 事件顺序：ThinkingDelta 一次性到达 → 同一 tool_use_id 的 ToolCallDelta 反复到达、输入逐步变长（没有 message_id，并行调用会交错）→ ToolCall + AssistantMessage → 可能有审批（PermissionResolved）→ ToolProgress（只有 Execute；`update.full_output` 是累计输出）→ ToolResult（并行时可能乱序）。
- 隐藏的用户消息：id 以 `context-`、`todo-sug`、`__internal__system-reminder__` 开头。
- 审批选项 `proceed_once` / `proceed_always` / `cancel`，只能用请求里给出的；Execute 的真实命令在 `full_command`；PermissionRequest 没有 id；PermissionResolved 的 `tool_use_ids` 可能为空。
- 回调没有超时；回调抛异常或 CancelledError 时 Droid 收不到回复，所以一律回复取消（`CancelPermission` / `CancelQuestion`）。
- 关闭：先取消读事件的任务，再 `close()`；droid 被杀后 `DroidProcessError` 会在 `close()` 时再抛一次。
- `Session.resume()` 没有 cwd 参数，droid 继承本进程 cwd：恢复时在 `cwd_lock` 里 `os.chdir`。恢复不回放历史，历史用底层 `load_session`。
- 无效模型 id 会被静默替换，会话中途可能收到 SettingsUpdated：界面显示 Droid 报告的实际模型。
- TokenUsageUpdate 是会话累计值，RunResult.usage 是单轮值；提示缓存空闲约 5 分钟失效。恢复的会话也接着数（2026-10-31 实机：关闭再恢复后 `tokenUsage` 与关闭前一致，再发一轮后与 droid 自己的 `.settings.json` 的 `tokenUsage` 逐项相等）；`load_session` 的结果带 `token_usage` / `inclusive_token_usage`（后者含子会话），`session_token_usage_changed` 通知带 `tokenUsage` 和 `inclusiveTokenUsage`。
- Windows 上 droid 用 Job Object 管住自己的子进程，宿主被强杀也不会残留。
- 上下文用量（状态栏显示的三个数）：窗口 = `Session.context().limit`（claude-sonnet/haiku/opus-5-5 都是 872000 = 1M 窗口 − 128K 输出）；已用 = `get_context_breakdown().last_call_compaction_tokens`（Droid 记录的最近一次模型调用：输入 + 缓存读取 + 输出，随会话保存，恢复的会话直接有数；`Session.context().used` 只是固定提示的估计，不跟对话走，别用）；自动压缩阈值 = `get_context_breakdown().context_budget`（默认 min(250000, 窗口)，用户的每模型 `compaction_token_limit` 可覆盖，某用户的设置里 claude-*-5-5 是 800000）。breakdown 不在高层 API 里，要经私有门 `Session._require_client()`（SDK 锁 0.5.0，`test_context.py` 里有测试守住）。droid 的通知（`session_compacted`、`session_token_usage_changed`）经 `Session.on_notification` 订阅。
- 「最近一次模型调用」不一定是对话本身的调用：会话标题由一次小的旁路调用生成（约 360 token，和第一轮同时跑，常常比第一轮晚结束），它会成为 `last_call_compaction_tokens`（2026-10-29 实机：Haiku 第一轮 22518，标题调用 357，状态栏曾显示 357）。所以每次调用的数字直接取 `session_token_usage_changed` 通知里的 `lastCallTokenUsage`（`inputTokens` 已含缓存写入；数字 = input + cacheRead + output，和 breakdown 口径一致；通知带 `sessionId`，不是本会话的不取）；小于「固定部分」一半的数字不当作对话大小（固定部分 = breakdown 的 `used_tokens` 减去 Messages 类别，Droid 的估计，实机约 10–13K；`core/context.py` 的 `plausible`）。`used_tokens` / `Session.context().used` 是估计值，比实际少很多（实机估计 13243，实际 22518），只用来做这个下限。
- 会话级 `compaction_token_limit`（`Session.update_settings`）：用户设置里该模型有 `compactionTokenLimitPerModel` 时被它盖过（例如某用户的设置里 claude-*-5-5 是 800000）；其他模型上立即生效，但不写进会话设置，到下一轮结束时又回到全局 `compactionTokenLimit`（全局默认 250000）。所以没法用它便宜地触发一次真实自动压缩；不要为测试去改用户的全局设置。- droid 可能不报错地把回合交给另一个模型服务（2026-10-29 实机：请求 `claude-haiku-5-5`，实际 `kimi-k3`，窗口和阈值都是 196608）；`get_context_breakdown().model_id` 报告实际服务的模型，界面一律显示 Droid 报告的模型。
- 附件：`Session.stream(prompt, *, images=(), files=(), …)`。图片 `Image.from_bytes(data, media_type=…)`（只收 PNG / JPEG / GIF / WebP，≤5 MiB）；文本 `Document.from_text(text, name=, mime=)`；PDF `Document(PdfDocumentSource(data=<base64>, parsed_data=<文字>, name=, path=))`（≤3 MiB）；坏数据抛 `InvalidAttachmentError`（`DroidError` 的子类，原因在 `.message`）。
- droid 在带图片的用户消息里另存一个文本块 `<system-reminder>Attached image local file paths: …</system-reminder>`（顺序：图片、提示、你打的字）：用户文字一律用 `core.attachments.typed_text`，不要把文本块拼起来。
- `load_session` 返回的 PDF 带着字节，虽然磁盘上的 jsonl 里 `data` 是空串（droid 另存在会话目录的 `attachments\` 下）；图片被 droid 重新编码保存，大小会变、像素尺寸不变。模型的 `no_image_support` 为真时 droid 会悄悄把图片换成一句说明、不报错，所以发送前自己拦（`SessionController.attachment_problem`）；`claude-haiku-5-5` 的值是 `False`。
- Qt / PySide 的坑（不是 SDK）：不要把捕获了 `QDialog` 的 lambda 连到信号，窗口随父窗口删除时进程崩溃，用绑定方法并连 `finished`；`QDragEnterEvent` 用 `QPointF` 构造会崩溃，用 `QPoint`（已弃用，压掉警告）；拖放要以「复制」接受，只提供「移动」的要拒绝（资源管理器会删原文件）；`QUrl.toLocalFile()` 返回正斜杠，`QFileDialog` 起始目录要 `str`；测试里想立刻删某个窗口，只对它调用 `sendPostedEvents(窗口, DeferredDelete)`，对 `None` 调用可能撞上前面测试遗留的对象而崩溃；`runJavaScript` 只带得回标量，对象/数组要 `JSON.stringify` 再 `json.loads`（`MainWindow.eval_js`）；`QWebEngineView.grab()` 在合成器忙时可能返回一帧异常图，连拍分析闪烁时别把单帧全变当成白闪。
- （迁移前的 Qt 控件界面有「第一个 QWebEngineView 出现时窗口重建约 140 ms」的问题，靠隐藏的 _gpu_surface 兜住；现在的窗口从构造起就是 QWebEngineView，问题不存在，兜底已删。Qt 的这个行为本身仍在：哪天窗口里又后加 QQuickWidget 会再遇到。）
- `factory_credits` 怎么算（2026-10-30 用 `docs/phase0b-context-cache.md` 里 6 个真实单轮数据拟合，`sandbox/fit_credits.py` 可重算；只有 claude-haiku-5-5 一个模型、输出只有 4 token，所以只是约束，不是证明）：`credits = ceil(倍率 × (input + 1.25 × cache_write + 0.1 × cache_read + w × output))`，缓存写 1.25、缓存读 0.1 各 6/6 吻合（别的取值最多 3/6），输出权重 w 在 5–6 之间（w=1 只吻合 1/6）。所以**输出（和思考）不能按 1× 估**；别的厂商的比例没验证（OpenAI 没有缓存写入，输出/输入比例也不同）。要显示积分就用 Droid 上报的 `factory_credits`，不要自己估算。官方文档（docs.factory.ai/pricing）只给了 5 小时 / 7 天 / 30 天三个相互独立的滚动窗口和 Plus ≈ 5× Pro、Max ≈ 10× Pro，没有公布每个窗口的固定积分上限；实时余量在设置 > Usage 或 CLI 的 `/limits`。本地模型表（`fixtures/models.json`，droid 0.251）里 claude-opus-5-5、gpt-6-sol-fast、gpt-5.6-sol 的倍率是 1.6。

token 换算，夹在 64 KiB 到 256 KiB 之间，窗口未知按 64 KiB；用户 2026-10-30 定的），新的优先；单条消息最多占预算的一半，超出的截掉后半并在前缀里注明（没有这个单条上限时，最新一条消息单独超过预算会一条都不带，也没有提示；2026-10-30 修）。窗口从哪来：模型列表里有的（Codex；API Provider 是用户填的 `maxContextLimit`，经 `ProviderStore.window_of` 进目录，没填是 0。2026-10-30 之前这一条只在文档里，代码漏传了 `window_of`，所以 API 模型的窗口恒为 0）直接用；Droid 自己的模型 SDK 不给窗口，要等新会话打开后它自己上报（`controller.context.window`），所以 `_switch_engine` reason?}], limits: {files, bytes}}}`，**每个附件都列出**（`core/handoff.carry_options`）：`as` 是带法（`text` 文字跟在消息后面 / `image`、`pdf` 作为文件随首条消息发出），带不了的 `as` 为空并写 `reason`（新模型不支持图片、Codex 读不了没有文字的 PDF、恢复出来的历史附件没有保留内容、只有空白的文本文件……），不能悄悄省掉；页面（`live.ts` 的 `askWhichAttachments`，`Overlays.tsx` 的 `CarryList`）弹带勾选框的对话框，**默认一个都不勾、Enter 不确认**、不可带的灰着，勾的文件比一条消息通常带的多时（`lib/carry.ts` 的 `carryOverage`，和 Python 的 `carry_overage` / `Overage.describe` 同一规则、同一措辞）页面写明**超了多少**，「换过去」按钮改成「超出了，仍然带上选中的 N 个，换过去」，由用户决定，再带 `attachments: [id…]`（用户确认超出时加 `overLimit: true`）重发（空数组 = 都不带；非字符串列表 → 「这个设置的值不合法」；未知或带不了的 MiB 是一条消息通常带的量（我们自己定的数，没查到 Droid / Codex 真有这个限制），文本附件换引擎时带的是文字，不算文件；超出了只说明、让用户确认。只有 `HARD_ATTACHMENTS`=50 个、`HARD_TOTAL_BYTES`=200 MiB（通常量的 5 / 10 倍，是我加的安全阀：这么多多半是误拖了一个文件夹，而且每个文件都要进内存、被页面 base64 + 输入框里的」算。加附件（`_admit`）时只有安全上限会拒绝，超过通常量照收，返回的 `over` 句子（「现在比一条消息通常带的量多 …，发送时会让你确认。」）显示在状态栏；发送（`_m_session_send`，**不管有没有交接附件**）时超过通常量**不发、答 `{ok: false, over: {count, total, files, bytes, text}}`**，页面弹「附件比一条消息通常带的多」对话框（`noEnter`：Enter 不确认，取消按钮有焦点，因为 Enter 刚刚才发出这条消息），用户点「仍然发送」后页面带 `confirmOver: true` 把同一条消息再发一次（`confirmOver` 不是布尔 → 「确认标记不合法」）。发送失败时 `_settle_inflight` handoff.attachments + 新附件` 一起发出，对话里只显示用户刚打的和刚加的；首轮成功后交接清掉，失败留着给重试。所以对话记录里要保留这些内容：`Attachment.slim()` 留着图片、文本附件的文字、PDF 提取出的文字，只丢有文字的 PDF 的字节（没有文字的扫描 PDF 整个留着，它只能以文件的形式带）；页面从来拿不到这些内容，`attachment_json`
