## 2. 发现与证据

### G1 / P1：Git 白名单仍能运行仓库程序

**位置**：`desktop/core/harness/permissions.py:416-438`、`:455-497`；`desktop/core/harness/shell.py:87-119`。

两个独立缺口：

1. **默认 hook 没检查**。`git_runs_own_programs` 只在配置出现 `core.hooksPath` 时检查 `post-index-change`，不检查默认的 `.git/hooks/post-index-change`。在独立临时仓库里加入索引文件、放一个只写无害标记的 hook，再改变该文件的 mtime，`code` 判定 `git status --short` 为 `allow`；通过真实 shell 工具运行后标记确实生成。给同一个目录显式配置 `core.hooksPath=.git/hooks` 后，判定才变成 `ask`。
2. **合法配置的 Tab 被漏掉**。`_git_settings` 用 `.partition(" ")` 拆 section/subsection，不识别 Tab。Git 2.50.1.windows.1 接受 `[diff\t"review"]`，也正确读取它的 `textconv`；预检却返回 `None`。有匹配 `.gitattributes` 的临时仓库里，`git diff` 被判 `allow`，真实执行了只写无害标记的 textconv 脚本。把 Tab 改成空格，同一设置就会被判 `ask`。

**边界**：这不表示每次 `git status` / `git diff` 都会运行任意程序。前提分别是默认目录已有对应 hook、或仓库配置了适用的 textconv。普通工具写 `.git` 已经会询问，但不能替代读取既有仓库时的防线。本轮没有改用户仓库的配置或 hook。

**建议**：用 Git 实际接受的配置语法判定，补默认和共享 hook 目录；白名单命令需要约束它的有效执行环境，而不只是命令文字。保留已经有效的 fsmonitor 中和，但不要把它当作整个 Git 隐式执行问题已关闭。

### G2 / P1：Git 预检重新引入审批前的网络文件访问

**位置**：`desktop/core/harness/permissions.py:388-413`、`:487-489`。

显式文件工具的 UNC 参数已修，但 `_git_root` 会相信本地 `.git` 文件里的 `gitdir:`，`_git_config_files` 接着读取目标下的 `commondir`、`config`、`config.worktree`。这些由元数据间接得到的路径没有经过 `fs_tools.is_remote_path` 的拒绝。

**复现**：隔离项目的 `.git` 写入 `gitdir: \\review.invalid\share\repo`。对 `Path.read_text` 加 spy，任何指向该测试主机的读取都在入口抛 `FileNotFoundError`，不发生网络访问。仅执行 `decide("code", ..., "git status")` 就观察到 **3 次远程路径读取尝试**，最终判定仍为 `allow`。

**影响与证据限度**：正式代码可能因此在用户批准命令前触发 Windows 网络访问/身份验证。这里只证明读取入口被调用，**没有连接真实 SMB，更没有证明凭据实际泄漏**。

**建议**：配置中的 `gitdir`、`commondir`、hook 路径也要在任何文件系统操作之前做网络/设备路径预检；检查无法安全完成时应返回不确定并询问/拒绝，不要把读取失败等同于“没有危险配置”。

### G3 / P1：最新一批工具结果超窗时，压缩没有可行的出口

**位置**：`desktop/core/harness/compact.py:147-179`、`:316-340`；`desktop/core/harness/loop.py:276-286`、`:330-339`。

`cut_points` 不包含列表末端，`choose_cut` 在任何尾部都装不下时仍返回最后一个切点。因此最新一批 `function_call + function_call_output` 必须整批保留；一旦它自己比窗口还大，压缩此前的用户消息无济于事。`compact()` 也不检查 `after < before` 或完整请求是否低于预算。

**复现**：真实文件工具读取 6 个临时中文文本文件，每个约 60K 字符；同一个假响应一次发出 6 个调用。窗口设为 272,000，假服务在后续请求按应用自己的估算器检查大小。结果：

- 压缩前模型视图约 **356,873** token，压缩后反而约 **356,934**；
- 含系统提示与工具声明的请求约 **372K**，仍发了出去；
- 假服务拒绝后，视图已经是 `[摘要, 整批调用及结果]`，`choose_cut` 返回 `None`；
- 回合最终 `failed`，并没有变成一个可发送的请求。

数字是**本地估算和假服务场景**，不是实际 OpenAI tokenizer/服务的测量。固定提示会随 AGENTS 内容变化，但“压缩后仍超过应用自己的预算、找不到下一切点”不依赖这一误差。

**建议**：给压缩增加可检查的后置条件；允许把已经完成的最后一个大步骤整体纳入摘要，并保留任务目标/最新用户要求。工具结果应按剩余总预算分配，而不只是每条限制 60K 字符。仍无法容纳时应停止并说明，不要声称已经缩到可用大小后原样超限发送。

### G4 / P2：摘要模型还没看到用户约束，它就已经被截掉了

**位置**：`desktop/core/harness/compact.py:185-208`、`:324-330`。

所有用户和助手消息先按 `TEXT_LIMIT=6000` 字符保留头尾，中间直接丢弃；之后才分块交给摘要模型。摘要提示要求保留用户的每条约束，但输入预处理已经让它做不到。

**复现**：9,926 字符的用户消息，中部放置一个明确的“不要改 billing”测试约束。整条文字只估算为 **2,837 token**，小于当时摘要分块预算 **12,000**，但该约束仍不在摘要请求里。原始日志保留它，模型视图没有自动取回该段原文的通道。

**建议**：区分用户要求和可丢弃的工具噪声；长用户消息应分块处理，不要在分块前无条件抹掉中间。关键约束应独立保留并有回归断言。这里不是证明模型摘要质量差，而是证明信息在模型看到之前就丢了。

### G5 / P2：用文本前缀猜“合成摘要”，会把日志索引算错

**位置**：`desktop/core/harness/compact.py:119-141`；`desktop/core/chatgpt/controller.py:653-658`。

`log_index` 只看 `view[0]` 的文字是否以 `SUMMARY_PREFIX` 开头，就减去一个“合成摘要”位置。它没检查当前是否真的存在 `SavedSession.compaction`。

**复现条件**：用户把 WittyCode 摘要连同前缀复制为新会话的第一条真实消息；没有旧压缩记录。后面有一组已配对的工具调用/结果，再发下一条消息触发压缩。

**观察**：正确的日志边界是 3，实际保存为 2，指向 `function_call_output`。首轮仍然成功，因为当轮直接使用压缩后的视图；下一轮重建视图才出现 `[摘要, 孤立工具结果, 用户消息, …]`，已没有与该结果对应的调用。探针的协议检查因此拒绝第二轮。

**边界**：普通自动生成的摘要记录不受这个前缀碰撞条件影响。真实 API 对该畸形输入的响应没有联网验证，但发出的结构不再满足本应用自己的调用配对约束。

**建议**：合成摘要是结构化状态，不应从用户可写的文本判断；显式传递视图起点/合成项数量，持久化时验证压缩边界不切开调用与结果。

### G6 / P2：运行中切模型，主请求和预算依据分叉

**位置**：`desktop/core/chatgpt/controller.py:352-372`、`:437-449`、`:629-646`、`:885-896`；`desktop/core/harness/loop.py:265-274`。

`update_settings` 允许 RUNNING 时修改模型，界面立刻更新；但正在运行的 `AgentLoop.model`、reasoning、instructions 在构造时固定。与此同时，`_Watch.prepare` 和 `_compact` 每次读取的是控制器的新模型。页面同引擎的模型切换没有禁用（`frontend/src/components/modelMenu.ts:65-77`）。

**复现**：假主请求开始后暂停，选择 Astra，再放行工具调用。请求顺序确定为：

```text
Sol   主请求
Astra 摘要请求
Sol   下一主请求
```

页面则显示 Astra / 272,000。因此不仅显示的模型可能不是真正执行者，压缩窗口、最低推理档、计入上下文的响应也会与主请求错配。

**建议**：明确“当前回合”与“下一回合”的配置所有权。如果设置下一回合才生效，页面应显示待生效，整个当前循环都使用旧模型的预算；若设计为下一步生效，就在请求边界原子更新模型、reasoning、instructions 和预算。不能只更新其中一半。

### G7 / P2：上一轮量到 383K，下一轮却只按字符重新猜

**位置**：`desktop/core/harness/loop.py:220-229`；`desktop/core/chatgpt/controller.py:437-449`、`:607-618`。

循环内部确实会用响应 usage 校正估算，但每个用户回合都会新建循环，`_measured` 又变成 `None`。已保存的 `context_used` 没有连到新循环的首步预算。

**复现**：假服务上一轮报告 **383,100**，切到 272,000 窗口，再发“继续”。高熵 ASCII 历史按字符公式加提示只估算约 **201K**，低于 85% 阈值，两个回合的请求序列只有 `main, main`，没有先压缩。

这里的 usage 是明确注入的假服务数据，用来验证“已知测量没有被使用”，不是声称某段文字在真实 tokenizer 下恰好是 383,100。后续仍有服务器拒绝后的补救，所以这不是“所有超限都会永久失败”，而是主动预算这一道门会错失它已经掌握的信息。

**建议**：记录测量所属的模型、视图版本和尾部位置，在新回合继续使用可比的测量；换模型时做保守处理。不要把其他视图/模型的数字盲用，也不要无条件丢弃唯一的实测依据。

### G8 / P2：已经压缩了，页面仍可能被旧缓存改回 383K/272K

**位置**：`desktop/core/app_core.py:1343-1350`。

`_compact` 正确发布 `used=None, compacted=True`。但 `_session_meta` 发现 `used is None`，就把整个 context 换成 `cached_meta["context"]`，没有区分“还没加载”与“主动失效、刚压缩”。

**复现**：真实 AppCore + ChatGPTController 接本地假 Responses，模拟带缓存恢复的会话；实际触发压缩后暂停主回答。控制器是 `compacted=True, used=None`，发给页面的却是旧缓存：`used=383000, window=272000, compacted=False`。下一次正常主响应报告 usage 后才会恢复；若这次请求失败，旧显示还会留着。

**建议**：实时的 `compacted` 是权威失效标记，不能被缓存覆盖；缓存回退应仅用于尚未获得实时状态的阶段，并验证模型/视图一致。

## 3. 对用户截图的解释边界

- `Context 383K/272K` 确实不是累计 Token；分母来自模型目录的 `context_window`，不是 ChatGPT Plan 代码里硬编码的 272K。
