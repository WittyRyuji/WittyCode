# WittyCode 自有 Harness 审阅（2026-11-06）

> 修复后的第二次审阅见 `docs/harness-rereview-2026-11-06.md`：第 7 节的修复覆盖了原始场景，但 R1、R2、R6 仍有边界缺口，另有停止超时续轮、Git 隐式执行、UNC 预解析和 HTTP 取消问题。以下保留第一次审阅及当时处理记录，不代表最新状态。

## 1. 结果与范围

**结论：已有可工作的单代理工具循环，但还不是能可靠承接长时间、可中断、可恢复任务的工程 Harness。最大的差距不是工具数量，而是上下文生命周期、执行安全、恢复语义和验证闭环。** 不建议先堆多代理或重写成复杂图框架。

本轮只审阅；不修改业务代码、前端、权限设置或真实账号。审阅对象是 `core/harness/`、`core/chatgpt/` 及其测试，并抽查 AppCore、hook 和项目指令的接线。

范围必须分清：

- **ChatGPT Plan** 用 WittyCode 自己的 Harness；本报告的循环缺陷针对这条路径。
- Droid / API Provider、Codex、Devin 的模型执行循环由各自上游运行；WittyCode 主要是协议适配和界面。Codex 的子任务面板存在，**不代表自有 Harness 已有子任务能力**。
- 对照的是当日实际读取的 Codex 开源实现、Claude Code 官方文档和 LangGraph 持久执行设计；不推测 Devin 等闭源内部实现，不给模型排名，不宣称所有成熟 Harness 都有同一套功能。
- “已复现”是本地离线探针看到的行为；“静态确认”是代码可以直接确认的缺项；真实服务溢出、崩溃恢复后的服务端拒绝等没有另花模型额度验证。

已有值得保留的基础：`Tools` / `Observer` 分离；流式文字与推理；工具参数校验、错误转结果；审批、引导和停止；正常取消时补齐工具输出；文件编码/换行保护；shell 输出与内存限额、超时和进程树清理；原子会话文件；跨引擎共享记忆与用量账本。现有相关测试本轮 **477 passed / 67.76 s**。这些基础不是“只有一个聊天 API 包装器”。

## 3. 与成熟 Harness 的关键差距

| 维度 | 已核对的成熟设计 | WittyCode 自有 Harness 现状 | 判断 |
| --- | --- | --- | --- |
| 上下文 | Codex 有主动/自动压缩；Claude Code 有自动压缩与压缩抖动退出 | 每次完整发送 `saved.items`，只有单个工具结果字符截断 | **P1，长任务基础能力缺失** |
| 持久执行 | LangGraph 区分检查点、任务完成结果和恢复；不把重新发输入等同于续跑 | 原子 JSON + 2 秒延迟快照；未完成调用无恢复修复 | **P1，有可复现的一致性缺陷** |
| 执行边界 | OS/容器隔离、明确的文件/网络权限边界；具体平台有差异 | 文本命令识别 + 直接继承宿主权限/环境 | **P1，现有保护声明可被绕过** |
| 工具调度 | Codex 按工具能力决定共享/排他执行 | `parallel_tool_calls=true`，实际逐个 `await` | P2，性能与引导响应性不足 |
| 可中断性 | 操作取消、进程/工作任务收尾、恢复结果有明确语义 | shell 清理较完整；文件工具的线程取消不等于操作停止 | **P1，有可复现的停止后写入** |
| 指令管理 | 分层规则、按需加载的技能/局部上下文 | 只找一个最近的根级 AGENTS，超过 24K 按头截断 | **P1，本仓库核心规则已被截掉** |
| 长任务工作流 | 可持久任务/验收状态、增量进度、可选停止验证 | 没工具调用就结束；步骤上限/未说完也记录为 done | P2，回合结束不等于任务完成 |
| 进程与产物 | 后台任务 ID、输出文件/分页、状态与取消、文件检查点 | 单次非交互 shell、最终一次性输出；没有通用产物仓库 | P2，调试和 UI 验证受限 |
| 扩展 | 通用 MCP、按需工具加载、技能与子代理 | MCP 为共享记忆定制的最小 stdio 子集；无技能/子代理 | P2/P3，不能当成完整插件平台 |
| 验证与评测 | 可复现任务集、故障注入、逐步 trace、同模型 A/B | 单测/fake 很多，但缺少任务级 Harness 效果基线 | P2，无法量化“升级是否更强” |

重要限定：Claude Code 官方文档明确写了**原生 Windows 的命令不受它的 Bash 沙箱保护**，WSL2 才可用该沙箱；沙箱也不覆盖它的所有文件工具/MCP/hook。因此不能用“顶级产品在所有平台都有完美沙箱”作为比较前提。WittyCode 的具体问题是当前规则可以产生错误的安全承诺，而不只是“没有沙箱”这四个字。

## 4. 缺陷与复现

### R1 · P1 · 受保护目录可经目录联接 + shell 绕过【已复现】

定位：`harness/permissions.py:125-135, 220-248, 251-282`；`harness/shell.py:258-276, 295-310`。

- 文件工具会解析真实路径并检查 `protected`，这部分是有效的。
- shell 对保护目录的检查是**命令字符串中出现的绝对路径**；相对名称、运行时组合和目录联接不构成同等约束。
- 白名单参数只有“看起来像绝对/越界路径”才被解析。`linked-private/marker.txt` 这种普通相对路径没有真实目标检查。
- 离线探针：项目外创建 `private/marker.txt`，放入无密钥的哨兵文字，设为保护目录；项目内建立指向它的目录联接。`read_file("linked-private/marker.txt")` 被拒，**`code` 档的 `shell("Get-Content linked-private/marker.txt")` 被允许，而且读出了哨兵**。

影响：不需要切到 full，也不需要额外批准这条被误判为只读的命令，就能绕过“任何工具都不能访问受保护目录”的声明。这里只读取了自己的测试文件，没有读取真实令牌。

建议：短期对不能证明安全的 provider 路径/链接/参数保守询问或拒绝，并统一保护路径语义；中期让命令运行在真正隔离的执行环境，凭据由宿主代理而不是暴露给任意同权限脚本。`shell._launch`（81-88）目前复制整个 `os.environ`，还应评估环境变量最小化。**扩展字符串黑名单不等于隔离；Job Object 也只解决生命周期，不是文件/网络沙箱。**

### R2 · P1 · 停止回合之后，文件线程仍可能写入【已复现】

定位：`harness/tools.py:176-197`；`harness/fs_tools.py:679-697, 812-824`；`chatgpt/controller.py:535-554`。

同步文件工具通过 `asyncio.to_thread` 执行。取消 await 方不会杀掉工作线程；Create/Edit 提交前也没有取消屏障。控制器此时可以结束旧回合、进入 READY，新回合可能已经开始。

探针在真实 `_plan_edit` 生成计划后暂挂线程，然后设置 `abort`、取消工具任务并等到 CancelledError，再释放线程：**文件在取消已返回之后从 before 变成了 after**。暂挂是确定性放大“读到计划到写入”窗口，写入仍是项目的真实实现。

建议：定义操作生命周期和提交边界；取消后等待不可抢占部分完成，再允许下一轮修改同一资源；提交前检查取消/文件版本。必要时使用可终止进程。不能仅在 `to_thread` 外再包一个超时就声称操作停止。

此外 Create/Edit 直接 `write_bytes`，没有原子替换、文件版本比较或文件快照。它们已有 diff，但 diff 不等于撤销能力。后续应加版本校验、同文件互斥、原子落盘及用户可选择的恢复，不应自动 `git reset --hard` 或覆盖用户改动。

### R3 · P1 · 自动存档可留下缺少工具结果的历史，重开不修复【已复现】

定位：`harness/loop.py:276-299`；`chatgpt/controller.py:234-250, 403-405, 591-606, 751-752`；`harness/store.py:123-148`。

正常 Python 取消路径会补 `INTERRUPTED`，这是正确的；**进程崩溃不执行这段清理**。

探针使用真实控制器、真实两秒延迟保存和一个只在内存中等待的工具：

1. 模型输出的 `function_call` 已入历史，工具还未完成。
2. 自动存档落盘，文件内存在该 call，但没有对应的 `function_call_output`。
3. 取出这一刻的文件内容，正常清理自己启动的任务，再恢复这份快照，模拟崩溃留下的磁盘状态。
4. `open_saved` 原样加载，缺失输出仍然存在；未结束的 `SavedTurn` 状态还是默认的 `done`。

影响：下次请求会继续携带违反本项目“调用必须有输出”合同的历史；真实服务是否拒绝没有另发请求验证，但本地无修复已确定。原子 JSON 只能保证文件完整，不能保证业务状态完整。另一个方向，副作用已发生、结果尚未落盘时，重试还可能重复执行。

建议：增加 durable operation journal，明确 `planned / approved / started / succeeded / failed / interrupted / unknown`。恢复时校验并修复调用配对，未完成操作显示为中断/结果未知；有副作用且结果未知的操作**不自动重跑**。按 call/run ID 记录结果与恢复策略，不宣称任意 shell 可 exactly-once。

### R4 · P1 · 没有上下文生命周期，长会话最终不可持续【静态确认】

定位：`harness/loop.py:47-50, 213-225, 239-248`；`chatgpt/responses.py:159-191`；`harness/store.py:38-65`。

- 每一步都把完整历史交给模型；没有请求前 token 预算、输出预留、分层压缩或溢出恢复。
- `MAX_STEPS=80` 限制的是请求次数，不是 token、工具总数或总时长。
- `clip_output` 只限制**单个**结果到 60,000 字符，不能限制累计上下文，而且中间内容没有产物 ID 可追回。
- 保存的上下文用量主要用于显示，不参与循环准入。
- 探针确认重复同一工具和参数会用完设定的全部步数，没有提前的无进展检测。

最关键的结构问题：**用于完整历史重建的记录和用于下一次模型请求的上下文是同一份 `saved.items`**，而 `SavedTurn.start` 是其中的索引。直接删旧项“压缩”会破坏页面历史、轮边界或工具调用配对。

建议先分开：完整、不可变的事件/对话记录；可重建的 `PromptView`；独立 artifact store。再加入预估预算 + 真实 usage 校正、保留近期步骤/未完成任务/用户约束的压缩、超限时可解释的暂停，以及按需检索旧产物。压缩本身也需要预算与防抖，不应无限“压缩→仍超限→再压缩”。不要未经验证就给 ChatGPT Plan 加文档明确禁止的 `max_output_tokens` / `truncation`，也不要假定它开放任何远端 compact 接口。

### R5 · P1 · 本仓库“规则”整节没有进入模型指令【已复现】

定位：`harness/prompt.py:15-16, 42-68, 94-97`。

本轮读取实际文件：`AGENTS.md` 有 **51,434 字符**；`AGENTS_LIMIT=24,000`；`## 规则` 起点在第 **50,736** 字符（零基索引）。因此按头截断的注入中不包含这整节，尾部交接要求同样未进入。末尾虽注明省略，但不保证模型会自行再读全文。

另外的离线探针确认：根项目启动时不会按所触碰文件发现子目录 AGENTS；从子目录启动时只选最近文件，父级规则不合并。现有测试还把“最近文件胜出”作为预期，但它不等于层级指令体系。

建议：把安全/工作区/不可做事项作为不能丢的结构化指令；根/父级和按文件作用域的规则按明确优先级合并；冗长调研材料从常驻规则中拆出，按需读取。截断要标明哪些来源/章节未加载并在 UI 可见。不是简单把常量从 24K 调大。

### R6 · P2 · Python 正则可阻塞 UI，线程并没有提供硬隔离【已复现】

定位：`harness/fs_tools.py:589-632`；`harness/tools.py:187-190`。

Grep 用 Python `re` 对各行做回溯匹配，既无执行超时，也无进程隔离；取消检查在文件之间，不在单次匹配内。CPython 的这类匹配可以持有 GIL，因此放进工作线程仍可能阻塞主事件循环。

离线探针只用 **25 字符**的一行（24 个 a 和末尾感叹号），模式 `^(a+)+$`：grep 耗时 **0.328 s**，预先排定的 asyncio 心跳额外延迟 **0.308 s**。较长输入的风险来自回溯算法，没有在真实窗口里扩大输入把它卡死。

建议搜索优先使用有硬超时、可终止的子进程，例如默认线性正则引擎的 ripgrep；保留 Python 正则语义时，也需隔离执行。单纯 `asyncio.wait_for(to_thread(...))` 不能解决持有 GIL 的匹配。其他文件工具也需要统一的时间、内存和输出预算。

### R7 · P2 · 并行标志不等于并行调度；引导在整个批次后才生效【已复现】

定位：`chatgpt/responses.py:43, 176-179`；`harness/loop.py:217-224, 283-292`。

- 请求允许模型一次给多个调用，实际运行却是 `for call in calls: await ...`。离线计数探针看到请求的 `parallel_tool_calls` 为 true，峰值同时执行数仍为 **1**。
- 第一项调用结束后即便收到“不要做剩下操作”的引导，已生成的第二项调用仍会运行，引导要等下一次模型请求才送到。这与当前文档“下一次请求读取”的语义一致，不应被描述成工具级即时改向。

建议：有限并发的只读调用、明确资源冲突的写操作串行、审批不锁死无关读取；在工具安全边界检查新引导，必要时暂停尚未开始的计划并交模型重规划。不能用无差别 `gather` 替换串行循环。

### R8 · P2 · 恢复、验收和可观测性仍主要靠模型自觉【静态确认】

定位：`chatgpt/engine.py:247-256`；`harness/loop.py:213-225, 253-279`；`chatgpt/controller.py:433-439`；`core/hooks.py:47-71`。

- 推理请求没有分类重试/退避、`Retry-After` 或 request 重试预算。网络抖动/可恢复 5xx 会结束当轮；鉴权文件重试不是推理请求重试。也不能把所有 429 都重试：套餐耗尽应直接引导管理用量。
- 没有跨步骤的无进展状态、时间/token/工具预算。80 步只是兜底。
- 没有工具调用就认为回合结束；步骤耗尽、回答不完整也保存为 `done`。这不是“代码已满足验收条件”。没有通用的持久任务状态和验证证据账本。
- 提示词确实要求跑测试，所以不是完全没有 verify；但它是提示，不是可选的工程停止策略。
- 现有 hook 只有发送前补上下文，且异常时跳过。不要拿这个 fail-open 的增强 hook 承担权限强制执行。
- 有 UI transcript、日志和累计用量，但没有完整的逐 step 持久 trace：输入上下文版本、response/request ID、时延、预算、权限决定和产物引用之间的可查询链路不足。`Finished.response_id` 也没有进入这条执行账本。

建议：按“尚无可见输出/尚无副作用”“流中断”“工具已执行但后续请求失败”区分重试；保留已完成工具结果，禁止重放整个回合碰运气。对自动长任务加入可配置验收清单和证据，不对每句聊天强加 critic 模型。检查命令必须尊重审批，也不能为了终态好看无限自动续跑。

### R9 · P2 · 工具链缺少一等能力【静态确认】

定位：`harness/tools.py:33-58, 145-152`；`harness/shell.py:195-241, 328-356`；`harness/mcp.py:81-128, 200-208`；`harness/toolset.py:29-30, 51-61, 80-87`；`chatgpt/controller.py:646-648`。

| 能力 | 当前状态/影响 | 建议优先级 |
| --- | --- | --- |
| 工具级结构化提问 | `answer_question` 固定 false；模型只能发文字，结束回合后再等用户 | P2，接已有 UI 提问能力 |
| 计划/任务状态 | 没有内置 update-plan / task 状态工具；进度主要在自然语言中 | P2，先做轻量持久任务表，不必先做任务 DAG |
| 长运行命令 | stdin 关闭；无 PTY、进程会话 ID、增量输出/后台状态；shell 默认 120 秒、最多 600 秒 | P2，构建/测试/调试先补进程管理和日志分页，PTY 视需求 |
| 大输出产物 | shell/循环保留头尾，中段没有可读 artifact ID；重开时也不能恢复全部原始输出 | P2，摘要 + 文件化完整输出 + 分页工具 |
| 安全补丁/文件恢复 | 有精确替换和 diff；没有多文件 patch、提交前版本校验、原子文件写或快照恢复 | P2，安全语义优先于增加编辑格式 |
| 官方资料/网页访问 | 没有 fetch/search；本轮靠获批 shell 临时抓公开网页 | P2，先受控 HTTP fetch；搜索服务按成本和需求接 |
| 浏览器与图像产物 | 用户发图已有支持；但文件读取拒绝二进制，工具结果只传文字，没有截图/图片产物回送模型的接口 | P2，做 UI 开发时很重要；不是声称模型不支持视觉 |
| 通用 MCP | 实际只接自家 memory；无 HTTP 传输、分页、list-changed 更新、resources、elicitation、完整取消；图片/structuredContent 被忽略 | P2，开放插件平台之前补合同 |
| MCP 信任 | `harmless` 信服务注解，直接免审批；服务器 instructions 直接进入高权限指令 | 当前自家 memory 可预置信任；接第三方前必须显式信任和隔离，不可照搬 |
| MCP 名称 | 净化并直接截到 64 字符，dict 建表时同名覆盖 | 通用接入前做稳定无冲突编码和检测；本轮未遇到真实冲突 |
| 分层规则/Skills | 无技能目录/按需发现；只有单份 AGENTS | P2，避免把所有知识常驻上下文 |
| 语义代码理解 | grep/glob 是词法；无 LSP 定义/引用/诊断 | P3，先保留可靠搜索，再按语言加 |
| 子代理/工作区隔离 | 自有 Harness 无 spawn/wait/message、独立上下文和预算，也不管理 worktree | P3，前面的状态/安全/预算完善后再做；不是最先补 |

shell 可以临时拼出不少能力，**缺少“一等工具”不等于绝对做不到**。差别是是否有明确权限、稳定接口、可观测结果和可恢复状态。

shell 进程树清理目前靠仍活着的父进程上的 `taskkill /T`，没有 Windows Job Object；父 shell 正常退出后后台子进程、宿主被强杀等场景不具备同等保证。这是静态生命周期风险，本轮没有额外制造孤儿进程验证。

MCP 的信任问题也不要过度泛化：目前接的是应用自己的共享记忆服务，不代表用户现有安装已经暴露任意第三方免审批执行。官方 MCP 规范明确要求，不可信服务器的工具注解不能被当作可信权限依据。

### R10 · P2 · “提供方无关”边界还没有真正形成【静态确认】

定位：`harness/loop.py:28-43, 239-248`；`harness/store.py:3-6, 59-65`。

循环直接 import `chatgpt.responses` 的消息、事件和 `build_request`，存档也是 Responses items。接口上的工具/观察者分离是对的，但运行时、上下文和存储仍绑定单一 wire schema。以后接 Anthropic/Gemini/BYOK 时，推理块、工具配对、图片/文件和压缩能力会泄漏到循环各处。

建议定义应用级 `Message / ToolCall / ToolOutcome / Usage / ModelCapabilities`，序列化、流解析、token 估计和提供方特有压缩放在 ProviderAdapter。保留现有简单循环，逐步迁移，不必现在推翻所有引擎，也不应擅自把用户的 API Provider 从 Droid 迁走。

### 第四批：基线稳定后再做子代理和优化

先建立同一模型、相同起点/权限的固定任务集，记录解决率、隐藏回归、改动范围、人工审批数、耗时、token、故障后的恢复成功率。对比旧/新 Harness，而不是同时换模型和框架。已有 scripted fake 很适合做故障回归，但不能替代任务级效果评测。

再加有独立上下文、预算、权限继承和工作区冲突管理的子代理；LSP、检索索引、更多提供方依需求加入。不要把“子代理数量”当作架构成熟度。

推荐保留当前简洁主循环，把职责放在它周围：

```text
Session / TaskState / ExecutionJournal
          |
ContextManager（分层规则、Skills、PromptView、压缩、Artifacts）
          |
ProviderAdapter（请求/流/能力/usage）
          |
ToolScheduler（并发、资源锁、审批、引导、取消）
          |
Policy + Runtime（文件、进程、网络、凭据边界）
          |
Evidence / 可选验证门槛 / 本地脱敏 Trace / Evals
```

这是一份补齐运行时合同的路线，不是建议为画架构图重写所有模块。先让单代理可靠，再让它更快、工具更丰富，最后才让多个代理协作。
