# Harness 正式复审：Token 与任务成功率（2026-11-15）

这是本任务**唯一一次正式审查**。在首轮实现、独立后端全量和 Windows 整机验证结束后，对照原请求、上次发现、最终差异与协议边界做审查；发现的阻塞问题集中修复，后续只做这些修复的定向验收和测试，不再开始第二轮全面审查。

上次报告是 `docs/harness-design-review-2026-11-14.md`；逐项实施、经济性对照、验证和未实施边界在 `docs/harness-fixes-2026-11-15.md`。不混入同时发生的界面任务。

## 复审确认并修复的九类遗漏

| 编号 | 严重度 | 发现、证据与处理 |
| --- | --- | --- |
| R1 | P1 | **模型与 OAuth 通用 HTTP 层仍自动跟随重定向。** 之前修过 Provider 的“测试连接”，没有覆盖这条通用路径。两个不同端口的本机 HTTP 服务，实际复现 POST 302 后转成 GET，把假 Authorization 转给第二个服务；普通请求和流请求都受影响。现在不跟随 301 / 302 / 303 / 307 / 308，向调用方返回状态，让用户修正地址，不转发凭据或请求体 |
| R2 | P1 | **Responses 拒绝文本被当成空回答。** 解析器只读 `output_text`，`refusal` 不显示，也不进可读历史；完整拒绝会触发多余的空回答重试。真的流解析器接本机脚本复现。现在拒绝文本流式显示，恢复、摘要和跨适配器转换也保留，不自动再问一次 |
| R3 | P1 | **已完成模型回合与已验收任务混为一谈。** 把 Stop Hook 的拒绝改成通知之后，`/goal` 仍可能照着 `GOAL: DONE` 清除目标。真的 AppCore + 假模型 + 拒绝 Hook 复现。现在保留模型回合的完成记录，但 Hook 否决会暂停并保存目标，不宣布目标已完成；下一次正常回合重置该标记 |
| R4 | P2 | **新建的流 HTTPS handler 没有继承显式 TLS 上下文。** 检查 opener 中的实际 handler 可复现；自定义受信 CA / TLS 策略可能失效。这是本轮新实现的遗漏。现在继承原 HTTPS handler 的 context 和 hostname 策略；没有通过关闭证书校验绕过问题 |
| R5 | P2 | **无关的 Provider 配置损坏可以阻断已有套餐会话。** 新的环境过滤会读取 Provider 引用变量，错误没有隔离。假 ProviderError 接真的套餐控制器复现，尚未发请求就失败。现在退到基础子进程环境并明确通知，不泄漏未知变量，也不阻止主会话继续 |
| R6 | P2 | **MCP 的坏元数据与启动定义没有完整隔离。** 无效 `inputSchema` 在错误清理之外解析；损坏的声明缓存可能直接抛 KeyError / AttributeError；Connections 定义无法构造时整个模型轮次初始化失败。真实本机 MCP 脚本、损坏缓存和假启动定义分别复现。现在合同解析和更新是一个受控事务，失败关闭子进程并保留旧合同；缓存损坏不使会话中毒；第三方命令定义失败时暂时跳过第三方 MCP、保留内置记忆并通知。冷启动错过等待期限也会说明“清单已固定，重新打开可用”，不静默隐藏工具 |
| R7 | P2 | **MCP 的分隔符本身仍可重名。** `("a__b", "c")` 和 `("a", "b__c")` 会变成相同名称，之前只处理了截断与非法字符。纯函数实跑复现。现在对带分隔符的原始名称也加成对定义的哈希后缀，最终重复仍明确拒绝，不把一个调用送给另一个工具 |
| R8 | P2 | **命令许可里的 cwd 绑定的是原字符串，不是解析后的目标。** 同一目录别名指向另一处时，键仍相同。用可控解析结果复现；现在按实际解析后的目录绑定，目录目标改变就需要重新批准 |
| R9（旧 A3） | P3；真实服务拒绝仍未验证 | **Chat 重放继续发不合法的工具参数文本。** 原始非 JSON、数组和字符串会回到 `function.arguments`，而另外两种适配器已归一为对象。现在无效对象重放为 `{}`，保留“参数错误、未执行”的工具结果，不执行坏调用；合法 JSON 对象的原始文本不改 |

对应回归为 `tests/test_harness_final_review.py` 的 15 个参数化用例；均只用本机服务、假流、临时设置或纯函数。普通 HTTP / 套餐 / API / Bedrock / MCP / 生命周期相关既有测试一起检查。真实认证、真实 TLS 服务和真实模型行为仍未验证。

## 仍存在的设计缺陷：下一步应优先什么

### 1. P1：摘要仍可能丢掉执行证据，不应只追求压缩比

`compact.render` 对一个工具结果只保留约 1,200 字符，对助手文字也有固定裁剪。离线探针把一条 **20,026 字符**工具结果中间放一个验收标记，摘要输入剩 **1,250 字符**，标记消失。模型即使写摘要完全正确，也无法保存根本没见到的证据。

因此“请求放得下”和“任务能可靠接着做”不是同一个验收条件。最新一批工具输出过大、不得不整步摘要时，这个问题尤其明显。现有用户原话保留和清单/编辑参数保真不能覆盖所有工具结果。

**建议优先实现**：完整工具结果落盘、把位置和连续可读范围交给模型；主上下文保留小摘要与文件引用；压缩摘要保留可核对的验收结果、未完成清单和引用。用“压缩后能否继续完成任务”的回放测试验收，而不只断言 token 减少。不要为省 token 无差别删除所有工具结果或旧推理。

### 2. P2：旁路调用的消耗仍不在主对话账本内

`chatgpt.side.ask` 处理文字后只返回字符串，丢弃 `Finished.usage`。标题生成、记忆整理用这条路径，调用有成本，但不会通过主会话的 `usage_series` / 请求诊断记进去。假旁路请求报告 123 输入、7 输出，返回了标题，主控制器仍没有这笔用量；本轮未改这套旁路接口。

**建议**：把“主对话 / 压缩摘要 / 标题与记忆”等请求种类单独归类记账，再给总计；必须保留原来源和模型归属、取消与迟到响应边界，不能把 API 调用记到套餐，也不能重启后重复计入。没有这项，界面数字不能被当成整个应用实际花费的完整测量。

### 3. P2：运行态存储与页面协议仍随历史增长

会话保存仍是完整 JSON 快照，请求体编码仍同步处理完整输入，页面仍频繁重发整个运行中的回合。哈希复用和把 Hook 校验移到线程里减少了两项开销，不等于消除了长会话的界面线程风险。单会话租约防止两个正常窗口互相覆盖，不等于全应用设置的事务和追加式执行日志。

**建议**：先拆不可变事件日志与模型上下文视图；写入采用有序后台队列，改动前的耐久检查点必须真正等待完成；页面按块/版本增量更新。必须测试停止、崩溃恢复、迟到写入、换引擎和多窗口，不宜只把同步保存包进一个无人等待的后台任务。

### 4. 恢复仍不是幂等执行或客观验收

网络续接保留历史、有限次重试并告知模型不要盲重做，解决的是“单次传输故障立刻结束任务”。对于结果未知的部署、发布、数据库或其他远程副作用，提示词不能替代幂等键、可查询的事务状态和用户确认。`GOAL: DONE` 仍是模型自评，不是通用的外部正确性证明。

**建议**：把可运行的验收命令/结果和恢复检查点结构化；遇到不确定副作用先核对状态，不能靠自动增加轮数“提高成功率”。后台命令、多模态工具结果、子代理还需要各自的权限、取消、结果预算和持久化设计，不是越多越可靠。

## 验证边界

- 没有调用真实模型，没有读写用户的实际账号、会话、设置或凭据。
- 这次修复没有默认启用新的套餐缓存字段、Claude 长寿命缓存或服务端压缩；不能宣称已验证真实命中率、费用下降或任务成功率百分比。
- 完整 Python、Windows 和前端结果及其先后顺序见修复报告；前端 QWebChannel PDF 预览的既有超时单独保留，不以其他绿测冒充通过。
- 来源名、配置或环境故障的恢复不保证所有第三方 MCP 都可用：命令列表构造失败时会暂时隔离整组第三方定义，需要用户修正 Connections；未默默改用户配置。
