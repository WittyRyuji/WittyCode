# 自有 Harness 设计复审（2026-11-14）

> 后续状态（2026-11-15）：本文件保留修复前的审查快照，不代表当前代码仍全部未修。逐项修复、未实施的设计边界和离线验证见 `docs/harness-fixes-2026-11-15.md`；本轮唯一正式复审及剩余设计问题见 `docs/harness-design-review-2026-11-15.md`。

用户：「再 review 一下当前代码，然后找出当前 harness 的设计缺陷。」

## 结论

没有改业务代码。把 `core/harness/`、`core/chatgpt/`、`core/llm/`、`core/connections.py` 和 `core/app_core.py` 里驱动回合的部分按当前提交（`aef76aa`）重读了一遍，可疑点都用真的循环、控制器、适配器和工具离线实跑。**真实模型 0 次，没有读用户的设置、会话和凭据。**

最要紧的三件事：

1. **历史只保证「调用和结果成对」，没有按每种接口校验能不能发。** 两种新出现的历史形状，按公开报告会让某些提供方拒绝之后的每一个请求，会话卡死（请求形状已离线实跑确认，真实服务的拒绝本轮没有亲自验证）：停在「思考完、工具调用还没写完」时留下的孤立推理项（Claude 直连和 Bedrock），以及 `developer` 角色的消息原样发给 Chat Completions 服务。前一条的停止／断流路径和后一条都是 11 月 13 日那批修复带进来的，现有测试没有覆盖。
2. **上下文更新是整份指令的全量快照。** 切一次 Plan／Auto、过一天、改一次权限、换一次模型、动一下技能，都往对话里永久追加一整份指令。`AGENTS.md` 有 24,000 字时每次约 7,900 token，9 次变更后对话里有约 71,000 token 的重复指令。
3. **「连接超时 20 秒」实际是「等响应头 20 秒」。** 首字节慢的服务（本机模型、会缓冲的网关）会收到同一个请求 5 次，然后这一轮以「连不上」失败。

其余发现是信任边界与声明不一致（环境变量里的密钥、MCP 自述的只读、按程序名记住的批准、应用自己的配置文件不受保护）、工具声明随 MCP 启动时序变化、失败后不续跑，以及所有 O(对话大小) 的工作都在界面线程上。

## 发现

### A. 历史的合法性没有按接口校验

循环的历史以 Responses 的项为唯一格式，其他接口靠适配器翻译。循环自己守的不变量只有一条：每个调用后面有且只有一个结果（`store._pair`、`compact.boundary_ok`）。11 月 13 日的修复让循环开始产生三种新的项，却没有逐个适配器验证这些形状能不能发。

| # | 级别 | 问题 | 证据 |
| --- | --- | --- | --- |
| A1 | P0（Claude 直连、Bedrock，依据公开报告）；Responses 未验证 | **孤立推理项。** 流失败或被停止时，已完成的输出项现在会进历史（`loop.py:490-500`）。如果模型已经思考完、工具调用的参数还在传（写大文件时这段有好几秒），历史末尾就只剩一个推理项，后面没有它引出的调用或文字 | 实跑。真的控制器接假服务，按停止后：存档是 `[user, reasoning]`，下一个请求的输入是 `[user, reasoning, user]`。Anthropic 路线的下一个请求里有一条只含 `thinking` 的 assistant 消息，Bedrock Converse 是只含 `reasoningContent` 的 assistant 消息。按公开报告，Anthropic 和 Bedrock 对这种消息返回 400「The final block in an assistant message cannot be `thinking`」，别的代理项目因此出现过「会话中毒」；本轮没有对真实服务验证。历史只追加不改写，所以之后每个请求都带着它。其他走 Anthropic 格式的服务（自带的 DeepSeek、MiMo 预设）是否同样拒绝，未验证 |
| A1b | P0（同上） | **空回答的恢复请求本身就是这种形状。** 模型只返回思考、没有文字也没有调用时，循环追加一条提示再问一次（`loop.py:362-372`）。带签名的思考块现在会保留，于是第二个请求就是「只含 thinking 的 assistant 消息 + 提示」 | 实跑：真的 Anthropic 流解析器加请求构造，第二个请求的消息是 `user / assistant[thinking] / user` |
| A1c | P0（同上） | **`/compact` 救不回来。** 压缩把末尾的推理项当成「属于后面的内容」，不会把它折进摘要 | 实跑：`ends_whole` 为假，选出的切点之后保留的仍是 `[message, reasoning]`。只有换到另一个主机的模型才能继续（别家的推理项不回传）；换回来又会带上它，直到之后某次压缩把它折进摘要 |
| A2 | P0（拒绝该角色的 Chat 服务，依据公开报告）；其余未验证 | **`developer` 角色原样发给 Chat Completions。** 上下文更新（`prompt.py:237-246`）和空回答提示都是 `developer` 消息。Anthropic 和 Converse 适配器把它当成 user，Chat 适配器把角色原样带出去（`chat.py:80-90`） | 实跑：发出的角色是 `system, user, assistant, developer, user`。DeepSeek 的 Chat 接口页列出的角色只有 `system`、`user`、`assistant`、`tool`、`latest_reminder`（本轮实读）；它对 `developer` 返回 400／422 是多个客户端项目的公开报告，Mistral 系也有，本轮没有对真实服务验证。本应用自带的 DeepSeek 预设走 Anthropic 格式，不受影响；自带预设里走 Chat 格式的有 OpenRouter、Fireworks、Groq、Gemini、Ollama、LM Studio 和「其他」，各家怎么处理这个角色未验证。压缩后最新规则仍以 `developer` 消息带着，所以压缩也不解决。会忽略未知角色的本机服务则是另一种后果：模型看不到「Plan 已关闭」，而系统指令里还写着 Plan 开着（未验证） |
| A3 | P3，未验证 | Chat 路线把不是合法 JSON 的调用参数原样放回 `tool_calls[].function.arguments`；Anthropic 路线把它换成 `{}`。会解析这个字段的服务可能拒绝 | 实跑看了请求形状，没有对真实服务验证 |

Responses 路线对「推理项后面没有输出项」和「推理项后面跟着一条没有 `id` 的合成消息」是否接受，没有验证。社区里有无状态用法下收到「was provided without its required following item」的报告，也有说 `store: false` 时不触发的。

**根因**：新的项类型加进了共用历史，却没有一层「发送前按接口归一化」，也没有「循环能产生的每种项 × 每种接口」的契约测试。只修这两处，下一种新项还会重演。

### B. 上下文和缓存的经济性

| # | 级别 | 问题 | 证据 |
| --- | --- | --- | --- |
| B1 | P1 | **上下文更新是全量快照，不是增量。** 首轮指令固定在 `instructions` 里；之后任何一处不同（日期、Plan／Auto、权限档、模型名、技能清单、服务器说明、`AGENTS.md`、思考语言），就把**完整的当前指令**作为一条消息追加进历史（`controller.py:538-545`）。来回切换不抵消：切回去又是一份 | 实跑，见下表。按文档的 Plan 流程（出方案 → 切 Auto 执行）每个任务至少多一份。压缩后保留最新一份，所以此后请求里长期有两份（首轮快照加最新规则）。旧的几份互相矛盾，要靠「以最新为准」这句话让模型分辨 |
| B2 | P2 | **工具声明随 MCP 启动时序变化。** 服务器一个接一个启动（`controller.py:321-340`），首轮总共只等 20 秒（`controller.py:343-345`）。没赶上的服务器，第一轮没有它的工具，第二轮才出现。工具声明在缓存前缀的最前面，一变整段重算 | 实跑（按比例缩短）：三个各需 8 秒的服务器串行约 25 秒才全部就绪；第一个请求只有前两个的工具，第二个请求多出第三个，工具哈希不同。内置记忆服务器因为预置了声明不受影响；这条只影响用户在 Connections 里加的服务器。服务器带说明文字时，还会再追加一份 B1 的全量指令 |
| B2b | P2 | **MCP 工具名截到 64 字符后可能重名**，后一个悄悄盖掉前一个（`toolset.py:43-44`、`74`）；`.` 和 `_` 归一后也会重名 | 实跑：同一服务器下两个前缀相同的长名字得到同一个名字 |
| B3 | P1，已知未做 | **压缩线和保留量只看窗口百分比。** 默认 85% 压缩，压缩后原样保留最新的部分，最多窗口的 25%。窗口 1,050,000 的模型（内置规格表里的几个 API 模型）在 892,500 才压缩，压缩后保留的原文最多 262,500，长对话里通常接近这个数，紧贴 272K 的长上下文价格线：第一次越线之后基本回不到线下 | 读代码加算术（`compact.py:47-50`、`148-150`，`settings.py:49`）。即 11 月 12 日审计的 C1，仍未实施 |
| B4 | P2，收益未实测 | **Claude 路线只用默认 5 分钟寿命的断点。** 桌面对话里两轮之间隔 5 分钟以上很常见，每轮开头都是一次全量写入（1.25 倍价）。官方有 1 小时寿命（写入 2 倍价），没有按「稳定前缀用长寿命」做策略 | 读代码（`anthropic.py:150-166`）加官方文档 |

### C. 请求失败和长任务

| # | 级别 | 问题 | 证据 |
| --- | --- | --- | --- |
| C1 | P1；真实服务未验证 | **20 秒的「连接超时」是等响应头的期限。** `urllib` 的一次 `open()` 包含建连和等响应头，现在给它 20 秒（`http.py:183`）。超时被归为连不上，属于可重试，而且此时还没有「已确认」标记 | 实跑（按比例缩短）：响应头 15 秒到，1 个请求，正常；30 秒到，服务端收到 **5 个**相同请求，这一轮失败，提示「连不上…：timed out」，总共约 145 秒。直连 OpenAI 和 Anthropic 的响应头很快，不受影响；首个 token 出来才发响应头的本机模型服务和会缓冲的网关会中。这是 11 月 12 日 L1（静默被当成连不上、同一请求重发）在响应头阶段的重现，由「连接和读取超时拆开」引入 |
| C2 | P2，设计取舍 | **确认之后的任何传输中断都直接结束这一轮**，不续跑。`/goal` 遇到失败的回合就停，目标只在内存里，重启即丢（`app_core.py:240`、`1814-1826`） | 读代码。已完成的输出项现在会留在历史里，本来可以用一个新请求接着做（不是重发原请求），现在要用户回复「继续」。长时间无人值守的任务，一次网络抖动就停 |
| C3 | P2 | **Stop Hook 说「阻止」，已经完成的回合被记成失败。** Hook 在循环正常结束之后才运行（`controller.py:568-570`），它的拒绝或非零退出码走的是失败分支 | 实跑：模型的回答完整显示，回合状态是 FAILED，存档里也是 `failed`，错误是「扩展连接未完成」。`/goal` 会因此停下，首轮的记忆前言会重发一次 |
| C4 | 已知未关 | 流里 120 秒没有任何数据就判死，没有按推理档位或提供方调整，高档位的真实静默时间仍未量过 | 即 11 月 12 日报告「需要真实验证的」第 2 项 |

### D. 权限和信任边界

没有操作系统沙箱是写明的前提，下面这些是在这个前提内，边界和自己的声明不一致的地方。

| # | 级别 | 问题 | 证据 |
| --- | --- | --- | --- |
| D1 | P1 | **环境变量里的密钥对模型运行的一切可见。** 界面上 API Provider 的密钥只能填环境变量名，密钥通常就在应用的环境里；而 shell 命令（`shell.py:122-130`）、MCP 服务器（`mcp.py:118`）、Hook（`connections.py:607`）都继承应用的完整环境。Connections 里 MCP 的 `env` / `env_vars` 是一份白名单，但启动时合并的是「完整环境加白名单」，白名单不起隔离作用 | 实跑：给进程设一个假变量，shell 工具直接读出它的值。凭据**文件**被层层保护（文本、参数解析、联接点），凭据**变量**完全敞开 |
| D2 | P2 | **保护范围只有 `<应用目录>/chatgpt`。** 同一目录下的 `models.json`（可以含内联密钥和「取密钥的命令」）、`connections.json`（可执行命令的信任登记）、设置和记忆都不在内 | 实跑：`full` 档下读、改这两个文件都直接放行，`read_file` 返回内联密钥；`code` 档会问。改 `models.json` 的 `baseUrl` 或「取密钥的命令」，等于让应用把密钥发到别处或执行任意命令 |
| D3 | P1 | **第三方 MCP 服务器自称只读就免批。** 工具注解带 `readOnlyHint`，或同时声明不破坏、不对外，就在任何档位直接运行，Plan 模式也放行（`mcp.py:76-78`、`toolset.py:96-100`）。这条规则是为内置记忆服务器写的，现在同样适用于用户接入的任何服务器 | 实跑：自称只读的 `drop_database`，`ask` 档放行，Plan 模式放行。MCP 规范写的是：客户端必须把工具注解当作不可信，除非来自可信服务器 |
| D4 | P1 | **「本会话不再询问」按程序名记。** 批准过一次 `git add`，之后所有不带管道和分号的 `git` 命令都放行 | 实跑：批准 `git add` 后，`git push --force`、`git reset --hard`、`git clean -fdx` 直接放行；批准 `python -m pytest` 后，`python -c "…rmtree…"` 放行；批准 `npm test` 后，`npm publish` 放行（`permissions.py:351-359`、`860-863`）。按钮写的是「同类操作」 |

### E. 状态、存储和界面线程

循环、HTTP 流的消费、存档、诊断和页面推送都在 Qt 的界面线程上（qasync）。下面每一项单看都不大，但都随对话或回合的大小线性增长，而且叠在一起。

| # | 级别 | 问题 | 实测（测试时的中位数） |
| --- | --- | --- | --- |
| E1 | P2 | **每次保存都重写整个会话文件。** 回合进行中只要历史有新增，最多每 2 秒一次，每个会改东西的调用之前再一次（`controller.py:985-1004`、`store.py:390-394`）。日志从不缩短，压缩也不减小它 | 2 MB 15 ms；10 MB 33 ms；30 MB 89 ms |
| E2 | P2 | **每个请求把全部历史项重新哈希一遍**做诊断（`diagnostics.py:46-55`），请求体的 JSON 也在界面线程上编码 | 10 MB：哈希 25 ms、编码 29 ms；30 MB：75 ms、91 ms |
| E3 | P2 | **每 40 毫秒把整个运行中的回合重新序列化并发给页面**（`app_core.py:96`、`1363-1392`），每个工具输出最多 60,000 字符 | 只量了 Python 一侧：一轮 60 个调用，每次 1.24 MB、3.4 ms；150 个调用，每次 3.09 MB、8.5 ms，文字流式输出时每秒最多 25 次。页面一侧的解析和渲染没有量 |
| E4 | P2 | **装了带 Hook 的插件后，每次查 Hook 都把插件目录重新哈希一遍**，同步执行。每个工具调用至少查 3 次（能否并发、调用前、调用后），每个 Hook 事件再起一个 PowerShell | 插件 2 MB／200 个文件：每次 13 ms；10 MB／800 个文件（在导入上限内）：每次 58 ms，即每个工具调用约 180 ms 卡住界面；每个 Hook 事件另需 200–280 ms |
| E5 | P2 | **没有单实例保护，会话文件后写覆盖。** 两个 WittyCode 指向同一个设置目录、打开同一个会话时，各自在内存里接着聊，各自整份写回 | 实跑：窗口 A 的第二轮写进文件后，被窗口 B 的写入整个盖掉，两边关闭后文件里没有 A 的那一轮。没有锁，也没有「文件已被别处改过」的检查 |

| # | 级别 | 问题 | 证据 |

## 查过、不成立或已有防护的

## 建议的修复顺序

每批先写会失败的测试再改，单独提交。

1. **先修会卡死会话的（A）。** 流失败或停止时，丢掉后面没有输出项的推理项；Anthropic 和 Converse 适配器在发送前去掉「以思考块结尾的 assistant 消息」，空回答恢复同样处理；Chat 适配器把 `developer` 映射成 `system`（只有官方 OpenAI 主机保留）；打开旧存档时修复已有的孤立推理项。补一张契约测试表：循环能产生的每种项（含失败路径产生的）乘以每种接口，断言发出的请求形状合法。
2. **响应头期限（C1）。** 建连和等响应头分开计时（建连 20 秒，等响应头用读取上限）；请求已经发出后的超时不算「连不上」，不盲目重发。
3. **增量的上下文更新（B1）。** 把指令分成稳定部分和易变部分（日期、模式、权限、模型），只追加变了的那几行；`AGENTS.md` 或技能真的变了才发那一节；压缩时前缀本来就要重建，顺势把快照换成当前指令，不再带第二份。
4. **工具声明的稳定性（B2）。** 服务器并发启动；记住每个服务器上次的工具声明，启动慢时先用它（和记忆服务器现在的做法一样）；声明按名字排序；重名时报错或加短哈希。
5. **信任边界（D）。** 给模型的命令一份过滤过的环境（去掉 Provider 条目引用的变量和名字像密钥的变量），MCP 和 Hook 只拿基础环境加声明的变量；保护范围扩大到整个应用目录；第三方服务器的注解不作为免批依据，由用户在 Connections 里逐个标记可信；「不再询问」按「程序加子命令」记，带内联代码的解释器不记。
6. **界面线程上的线性工作（E）。** 存档改成追加式日志加定期快照；诊断的哈希按项缓存；页面推送按块增量；Hook 的来源哈希按文件时间缓存或放到线程里；设置目录加实例锁，或第二个窗口对已打开的会话只读。
7. **长任务（C2、C3）。** 确认后的网络类中断，在已保留输出项的前提下有限次地用新请求续跑并明说；目标状态落盘；Stop Hook 的「阻止」不再把回合记成失败。

需要真实验证的（都未做，等用户给调用上限）：

1. Responses（套餐路线）对孤立推理项、对「推理项后跟一条没有 `id` 的合成消息」是否接受：2–3 个小请求。
2. Chat 格式的常用服务对 `developer` 角色是拒绝、接受还是忽略：每家 1 个小请求。
3. 本机模型服务在长提示下多久发出响应头：不调用付费模型。
4. 高推理档位下流里最长的静默时间（上一份报告留下的）。
